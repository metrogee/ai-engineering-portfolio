Project 1: guided bootcamp projectRBAC in progress

DocuChat, a backend API

A document-focused Python backend built in the Mastering Backend AI Engineering Bootcamp. It's how I'm learning to design and build the infrastructure behind a modern application, using FastAPI for the API layer, PostgreSQL for storage and SQLAlchemy for database access.

The problem
Apps with user accounts and private resources need more than endpoints that return data. They need a backend that authenticates users, validates requests, stores information reliably and controls access to protected operations.
The solution
Routes, services, repositories and models are kept separate, so HTTP handling, business logic and database operations don't tangle. Authentication runs through reusable dependencies.
Security
Passwords and refresh tokens are hashed. Access tokens expire after 15 minutes and refresh tokens after seven days, signed with separate secrets.

Project 2: collaborative group projectProposed solution

AI-Powered Public Transportation Prediction System

A group project about a familiar problem: people in Nigeria lose a lot of time waiting for buses and other public transport, with no clear idea how long the wait or the journey will be. This card sets out the solution our group proposed.

The problem

Many people in Nigeria spend a long time waiting for buses and other public transport. They also face heavy traffic, overcrowded vehicles and uncertainty about how long a journey will take. Transport operators find it hard to know where more of their services are needed at different times of the day. The result is wasted time, overcrowding and poor service.

Who it's for

Passengers who use buses, BRT, danfo, keke and other shared transport. Transport operators can also use it to see where and when more passengers are likely to need transport.

The proposed solution

An AI-powered system that tells people how long they may wait for transport and how long their journey may take. It also tells operators when and where many passengers are likely to need their services, so they can be available where they're needed.

How it works

  1. A passenger enters where they are going
  2. The system checks available routes and current information
  3. AI studies the information
  4. The system estimates the waiting and travel time
  5. The passenger receives the estimate and chooses the most suitable option

Operators can also see where passenger demand is expected to be high and plan for it.

Where AI is needed

Normal software shows routes and information. AI predicts what is likely to happen, using past traffic conditions, passenger numbers, time of day and current road conditions, to estimate:

  • How long a passenger may wait for transport
  • How long a journey may take
  • Which routes may be very busy
  • Where more passengers are likely to need buses or keke

Expected outcome

  • Less time spent waiting for transport
  • Better journey planning for passengers
  • Less overcrowding on busy routes
  • Operators know where more buses are needed
  • A better overall transport experience

Risks and limitations

  • Wrong predictions: accidents, road closures or sudden traffic can affect accuracy
  • Lack of information: good predictions need enough reliable data
  • Internet access: people without smartphones or reliable internet may struggle to use it
  • Privacy: any personal information collected must be protected

How success would be measured

  • Whether passengers spend less time waiting
  • How accurate the predicted waiting and travel times are
  • Whether overcrowding falls on busy routes
  • How satisfied passengers are with the information

01

Problem

A document-focused application needs a backend that can manage user accounts, communicate through predictable API endpoints, store data in a relational database and restrict access to protected functionality.

Without a clear architecture, authentication and database logic end up tied to individual routes, which makes the system hard to test and extend.

02

Solution and architecture

I structured DocuChat around separate routes, services, repositories and database models. Routes receive requests and return responses. Services handle application logic. Repositories perform database operations. SQLAlchemy models define the persisted structures, and PostgreSQL stores the relational data.

03

Authentication

I implemented a JWT-based flow with separate access and refresh tokens. Access tokens are short-lived. Refresh tokens last longer and are used to get new access credentials. Password hashes and refresh-token hashes are stored instead of the original secrets, and the authentication dependency validates the token and loads the user before a protected endpoint runs.

15 minaccess-token expiry
7 daysrefresh-token expiry
2 secretsseparate signing secrets for access and refresh tokens

Authentication flow for a protected request

  1. Incoming request arrives at a protected endpoint
  2. Extract the bearer token from the request
  3. Verify the JWT
  4. Validate token type and expiry
  5. Identify the user
  6. Retrieve the user from the database
  7. Authorize access to the requested resource
Authentication and authorization are different. Authentication establishes who is making a request. Authorization decides what that user may do. In DocuChat, JWT validation and database-backed user checks form the authentication layer, and the RBAC work adds a more granular permissions model than broad role checks.

Testing

I started a pytest suite with unit tests and API integration tests, using HTTPX and FastAPI's TestClient.

What the tests caught. While I was expanding RBAC, the integration tests exposed a missing roles table in the test database. Passing unit tests did not mean the whole application worked with its database.

AI engineering relevance

DocuChat is currently a backend engineering foundation for document-oriented applications. Its architecture and data-access components are relevant experience for building the infrastructure around AI features.

A proposed direction, not a feature. A future AI-enabled version could connect document processing and retrieval to a language model so users can ask questions about their documents. None of that is implemented yet.

What I built

  • API endpoints with FastAPI
  • Application logic split into routes, services and repositories
  • A PostgreSQL connection through SQLAlchemy
  • Schema changes managed with Alembic migrations
  • User registration and login
  • Password hashing instead of plaintext storage
  • JWT access tokens (15-minute expiry) and refresh tokens (seven-day expiry)
  • Separate signing secrets for access and refresh tokens
  • Refresh-token hashing, storage, rotation and revocation logic
  • Authentication dependencies for protected endpoints
  • Custom application errors with centralized handling
  • Authorization checks for restricted roles
  • Data-access components for users, refresh tokens and documents
  • Unit and integration tests with pytest and HTTPX / TestClient
  • The start of database-backed roles and permissions

Challenges and lessons

Translating concepts into Python

The bootcamp's original material meant translating backend concepts into Python while keeping the intended architecture. It pushed me to understand what each layer is for instead of copying patterns.

Managing authentication securely

Access tokens, refresh tokens, token-type checks, password hashing and rotation all needed careful handling of token validity and session security.

Keeping schema and models aligned

SQLAlchemy and Alembic taught me to treat schema changes as explicit, version-controlled changes.

Testing database-backed behaviour

Testing raised problems with test isolation, database state and making sure the test database has the schema the current models and migrations need.

What I learned

  • How a FastAPI request moves through the backend layers
  • How to keep business logic separate from database operations
  • How JWT access and refresh tokens serve different purposes
  • Why password hashing and token revocation matter
  • How relational models and migrations work together
  • Why custom error handling makes an API more consistent
  • How to approach automated testing and investigate integration failures
  • Why authorization should be designed explicitly, not added afterwards
  • Why working software needs clear documentation and reproducible tests
